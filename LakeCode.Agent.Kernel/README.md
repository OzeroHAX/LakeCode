# LakeCode.Agent.Kernel

Первая версия нативного F#-ядра. Пока существует рядом с `LakeCode.Agent`: провайдеры, инструменты, Core и CLI на него не переключены.

## Граница ответственности

- `Run` — чистое накопление и проверка потокового ответа модели.
- `SessionState` — функциональная машина: `update` получает состояние и вход и возвращает новое состояние с упорядоченными эффектами либо ожидаемую ошибку команды. Единственный `Work` содержит данные текущего ожидания; `RunPhase` и snapshots вычисляются из него, отдельно не поддерживаются. Публикация события — один из эффектов, а не третий список в результате перехода.
- `Session` — один владелец состояния на `MailboxProcessor` и один исполнитель эффектов. Только он принимает входы, фиксирует snapshots/журнал и вызывает подписчиков. Модель, policy и инструменты исполняются вне mailbox и присылают результаты; долгий I/O не блокирует приём отмены. Отдельной очереди доставки событий нет.
- `Model`, `Tool`, `Policy` — небольшие records с функциями. Реализации SDK, файлов, процессов и прочего I/O находятся снаружи и могут быть написаны на C#.
- `History` — неизменяемая история с закрытым представлением, проверкой сообщений и безопасным откатом.

Нет зависимости от старого ядра, MAF, UI, провайдерских SDK или функционального фреймворка. FSharp.Core подключается SDK F#-проекта. Порядок исходников явно задан в fsproj.

## Публичные операции

- `Session.EventOccurred` — основной live API: обычное .NET-событие с делегатом `Action<JournalEntry>` для подписки UI. В F# доступны `AddHandler`/`RemoveHandler`; в C# — `+=`/`-=`.
- `Session.Start(prompt, ?cancellationToken)` возвращает `Result<RunHandle, SessionError>`: запрос принят либо отклонён как `Busy`/`Closed`.
- `RunHandle.Completion` возвращает окончательный `RunResult`. Исход — `Completed`, `Canceled`, `Stopped` или `Failed`; состояние `Running` результатом не является.
- `Session.Cancel(run.Id)` запрашивает отмену именно этого запуска. Для другого/завершённого запуска возвращается `false`.
- `Session.Snapshot` — согласованное представление текущей истории, фазы запуска и последнего результата.
- `Session.ReadEvents(after)` — дополнительное чтение журнала после указанного номера; начальный номер — `0L`.
- `Session.WaitForEvents(after, cancellationToken)` — дополнительный pull API. После закрытия и прочтения всех записей возвращает пустой список; для обычной подписки UI не нужен.
- `Session.Rewind(point)` применяет точку, полученную из `History.rewindPoints snapshot.History`. Во время запуска возвращает `Busy`.
- `Session.Close()` запрещает новые запуски, запрашивает отмену текущего и ждёт его завершения. Повторное закрытие возвращает ту же задачу. Поддерживается `IAsyncDisposable`.

Модель, инструменты, policy и ограничения передаются при создании сессии и не заменяются во время запуска. Адаптеры не должны читать изменяемую глобальную конфигурацию вместо захваченных значений. `Start`, `Cancel` и `Rewind` синхронно ждут короткого ответа владельца, не завершения внешней операции; snapshots и журнал читаются без обращения к mailbox. `Close` ставит команду в очередь входов и возвращает одну общую задачу закрытия.

## Model/tool loop

1. `BeforeRun` выполняется до добавления пользовательского сообщения, как в старом Agent.
2. После успешной подготовки пользовательское сообщение добавляется в историю.
3. Запрос модели формируется из текущей истории и захваченного каталога инструментов.
4. `ModelAccess.Reply` и `ModelAccess.Stream` поступают в общую модель ответа; полный ответ фиксируется в истории.
5. Вызовы инструментов проходят `DecideTool`: `Allow`, `Deny reason` или `Stop reason`.
6. Инструменты выполняются последовательно, в порядке первого появления вызовов в ответе. Полученный результат фиксируется без последующего преобразования; отмена его не стирает.
7. После группы инструментов запрашивается следующая модельная реплика; отсутствие вызовов завершает запуск.

`Policy` остаётся общим record из трёх функций: `BeforeRun`, `DecideTool`, `AfterRun`. Дополнительных review/error hooks и преобразований запросов или результатов в ядре нет. Для наблюдения служат `EventOccurred` и дополнительный API журнала.

`RunOptions.MaxTurns = None` не ограничивает число обращений к модели; `Some n` требует положительного значения. `RunResult.Turns` считает начатые модельные шаги, включая прерванный шаг.

`Policy.none` разрешает вызовы; подготовка и завершение ничего не делают. Это не sandbox: ограничения доступа и approvals задаёт host через policy, а технические гарантии путей, атомарности и permissions обеспечивает реализация инструмента.

## Streaming и владение данными

- `ModelUpdate.Text` и `Thinking` сохраняют порядок в журнале. Reasoning не добавляется в модельную историю.
- `ToolStarted` объявляет id и имя, `Arguments` относится к открытому вызову, `ToolReady` передаёт полный вызов с JSON object arguments. Для обычного ответа достаточно `ToolReady` без предварительного start.
- Повторный id, изменение имени или незавершённый вызов при обычном окончании потока считаются ошибкой протокола.
- `CallId` уникален в сохранённой ветке истории. После отката удалённые ids больше не заняты.
- JSON аргументов, schemas и структурного progress клонируется при захвате. Аргументы полного вызова и progress захватываются до помещения во входную очередь. Producer обязан сохранять исходный JsonDocument живым до передачи значения ядру, а не освобождать его до yield/return.
- Чтение модели ждёт подтверждения обработки каждого update перед продвижением producer. При ошибке протокола producer останавливается, его iterator освобождается, и только затем машина завершает запуск. Ошибка освобождения не стирает уже установленную ошибку протокола.
- Изображения содержат оригинальные `ImmutableArray<byte>`. Декодирование, фактический формат, лимиты и поддержку изображений моделью проверяет адаптер. Изменять backing storage immutable bytes после передачи нельзя.
- Progress относится к конкретному запуску и вызову; после возврата инструмента поздние отчёты не принимаются.

## Прерывание и отмена

При отмене или ошибке полученный текст сохраняется как `AssistantReply` со статусом `Interrupted`. В историю попадают только полностью полученные tool calls; незаконченный JSON вызова не выдаётся за готовый вызов. Полностью полученные, но не выполненные вызовы закрываются явным `Skipped`.

`ToolResult` различает:

- `Success` — получен успешный результат;
- `Failure` — инструмент вернул известную ошибку;
- `Skipped` — инструмент не запускался;
- `Interrupted` — вызов начат, но результат не получен; побочные эффекты могли произойти.

Адаптер модели получает `ReplyStatus.Interrupted` и эти исходы явно. Он должен корректно передать их смысл в модельный протокол либо явно отклонить неподдерживаемое представление, а не молча объявлять прерванный ответ полным.

Отмена кооперативная. Ядро передаёт token, но не отсоединяет неотменяемую операцию: сессия и Close ждут её. Если результат всё же получен после отмены, он сохраняется, однако следующий инструмент или модельный шаг не запускается. Автоматических повторов нет. Отмена и rewind не откатывают побочные эффекты.

## Завершение и диагностика

Окончательный результат публикуется только после `AfterRun` и освобождения cancellation source. `AfterRun` получает `CancellationToken.None` при любом основном исходе запуска.

Ошибки завершающего hook и cleanup добавляются в `RunResult.Diagnostics`, но не заменяют основной исход. Если после ошибки протокола возникает исключение при освобождении потока модели, оно также сохраняется как диагностика. Исключения операций сохраняются отдельно в `Session.Faults`; они не попадают в сообщения, snapshots или события как exception objects. Faults могут содержать приватные провайдерские подробности: host не должен автоматически отображать или сериализовать их. Ошибки подписчиков также доступны здесь со Stage `event subscriber`, не меняют исход запуска и не порождают рекурсивных уведомлений. `Fault.Run` имеет тип `RunId option`: у ошибки подписчика на событие сессии, например откат, запуска может не быть.

Ожидаемые ошибки инструмента возвращаются значением `ToolResult.Failure`. Неожиданное исключение инструмента завершает запуск, оставляя неопределённый результат начатого вызова явно прерванным. Ошибка политики не означает разрешение.

Нарушение внутреннего runtime-инварианта — программный дефект, а не штатный tool result: приём новых запусков закрывается, отмена запрашивается у внешних операций, их завершение и cleanup ожидаются вне владельца. После cleanup задачи Completion и Close faulted исходным исключением, оно доступно в Faults. Успешное завершение при таком дефекте не имитируется; поздние результаты не меняют другую ветку или новый запуск.

## История, откат и восстановление

Отдельного checkpoint API нет. Как в Core, доступны границы:

- перед пользовательским запросом;
- после assistant message без tool calls;
- после всей группы результатов инструментов.

Точка привязана к id последнего сообщения префикса, поэтому устаревшая точка не может попасть на одноимённую позицию другой ветки. При откате сбрасывается LastRun и добавляется `Rewound`; полный журнал наблюдений сохраняется, а текущая модельная история укорачивается.

`History.ofMessages` проверяет восстановленные сообщения и запрещает открытый tool batch. Готовую историю можно передать новой `Session`. Snapshot во время работы предназначен для наблюдения: его History может содержать открытый batch, а текущий draft доступен в RunView и событиях. Такой snapshot не обещает восстановление внешней операции. Для сохранения окончательной истории host ждёт Completion.

Файловая persistence, формат сериализации F# unions, UI-проекция, сброс eval и фоновых задач при откате принадлежат host. Ядро не делает их скрыто.

## Подписка UI и журнал

Машина возвращает эффекты `Publish`, а исполнитель поднимает `EventOccurred` в одном месте. Перед исполнением эффектов `Session` атомарно фиксирует snapshot и записи журнала с возрастающим `Sequence` и принадлежностью `Run`. Единственный владелец синхронно вызывает подписчиков в порядке событий, вне блокировки snapshot/журнала. Отмена, progress и rewind не могут обогнать предыдущую публикацию. Исключение подписчика сохраняется в Faults, не мешает остальным подписчикам и не меняет исход запуска.

Обработчик UI только ставит обновление в очередь UI-потока: не рисует контролы, не выполняет I/O и не ждёт завершения запуска. Медленный подписчик задерживает обработку следующих входов и запуск следующих эффектов. Из callback нельзя синхронно вызывать `Start`, `Cancel` или `Rewind`: это обнаруживается и завершается InvalidOperationException вместо deadlock. Snapshot читать можно; `Close` можно запросить, но нельзя ждать его задачу в обработчике.

Подписка live, без автоматического проигрывания прошлого. Набор обработчиков захватывается при публикации; отписка не прерывает уже начатый вызов. Отдельного фонового диспетчера или очереди уведомлений нет. Обычный `RunFinished` публикуется до завершения Completion; перерисовка UI и обработка его очереди при этом не ожидаются. Входная очередь mailbox — механизм владения состоянием, а не очередь отображения.

В C# при уже созданной `session` подписка может просто собирать обновления в потокобезопасную очередь:

```csharp
var updates = new System.Collections.Concurrent.ConcurrentQueue<LakeCode.Agent.Kernel.JournalEntry>();
System.Action<LakeCode.Agent.Kernel.JournalEntry> onEvent = updates.Enqueue;
session.EventOccurred += onEvent;
```

UI-поток забирает записи из очереди по порядку. При закрытии контроллера нужно выполнить `session.EventOccurred -= onEvent`. В F# тот же делегат подключается через `session.EventOccurred.AddHandler(handler)` и отключается через `RemoveHandler`.

Журнал без ограничителя и без потерь хранится в памяти на протяжении жизни объекта сессии, в том числе доступен после Close для чтения последних событий. Это не event sourcing и не автоматическая persistence. Host отвечает за lifetime сессии и необходимое внешнее хранение. Snapshot содержит историю и текущий запуск, но не весь прошлый reasoning/progress: для восстановления такого отображения нужен журнал. UI фиксирует streaming-ответ при `MessageAdded(Assistant ...)`, а не добавляет второй экземпляр; `RunFinished.Text` не нужно дописывать ещё раз.

## Проверка

Из корня репозитория:

```text
dotnet build LakeCode.Agent.Kernel/LakeCode.Agent.Kernel.fsproj
dotnet build LakeCode.Cli/LakeCode.Cli.csproj
```

CLI пока не ссылается на этот проект, поэтому его сборка не заменяет отдельную сборку ядра. Тесты и приложение запускаются только по отдельному запросу пользователя.
