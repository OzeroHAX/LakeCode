# LakeCode.Core

Независимое от SharpConsoleUI ядро. CLI ссылается на Core, обратной зависимости нет.

## Три контракта

- **Команды** (`Conversations/ConversationCommand.cs`) — намерения пользователя. `ConversationService.Execute` возвращает принятие команды, а не завершение генерации. Отправка фиксирует неизменяемый профиль подключения, модель, reasoning и собственную копию оригинальных байтов вложений.
- **События** (`Conversations/ConversationEvent.cs`) — произошедшие факты: начало ответа, текстовые фрагменты, вызовы инструментов, завершение, ошибки и запросы решения. `EventOccurred` передаёт envelope с последовательным номером, ID сессии и запроса. Подписка не запускает агент и не воспроизводит старые события.
- **Состояние** (`Conversations/ConversationState.cs`) — текущие флаги выполнения, очередь, доступность операций, заголовок и статистика. `State` доступен сразу; `StateChanged` уведомляет о новом снимке. `GetConversation()` возвращает отдельный снимок истории и восстановленного черновика.

Сервис один раз читает поток MAF и владеет сессией, очередью, отменой, rewind и сохранением. Изменения состояния и публикация уведомлений сериализованы внутренней блокировкой. Обработчики уведомлений должны только ставить обновления в очередь своего представления: не блокировать, не бросать исключения и не выполнять команды синхронно из обработчика. CLI переводит уведомления на UI-поток в `ChatController`.

Ответы на вопросы и разрешения — отдельные команды с ID взаимодействия. Они не ожидают завершения генерации. Повторные и запоздалые решения не принимаются; отмена снимает ожидание и публикует его завершение.

Запрос пользователя сохраняется до внешнего обращения. Следующий запрос начинается после финального сохранения предыдущего. `FinishAsync` ожидает работу и записи очереди, включая финальное сохранение при shutdown. Выполненные побочные эффекты не откатываются при отмене или rewind. Восстановленная очередь видна, но остаётся на паузе до явного запуска.

`Attachments` содержит оригинальные байты и общую проверку изображения; clipboard, выбор файлов, PixelBuffer и превью остаются в CLI. Используется MAF 1.24.0. Формат сессий версии 3 хранит ProviderId и метаданные выбранной модели; версии 1 и 2 читаются как сессии исходного WikiVibe-подключения. Rx-пакеты и универсальный event bus не используются.

## Провайдеры

`Providers/ProviderRegistry.cs` владеет неизменяемыми профилями, `ProviderStorage` сохраняет их в `~/.lakecode/providers.json` независимо от рабочего каталога. Запись атомарная; на Linux каталог создаётся с правами 0700, файл — 0600. Ключи хранятся без шифрования. Повреждённые настройки не сбрасываются автоматически; пути через символические ссылки отклоняются. При отсутствии файла доступен исходный WikiVibe-профиль с ключом из `WIKIVIBE_API_KEY`; первый успешный save/delete записывает текущий список в файл, который затем имеет приоритет над переменной окружения.

CLI: `/providers` — добавление, изменение и удаление подключений и их моделей; `/models` — выбор пары провайдер/модель. Профиль содержит стабильный ID, revision, название, протокол OpenAI или Anthropic, API mode Responses/ChatCompletions для OpenAI, базовый URL, ключ и модели. Для OpenAI указывается API base URL (обычно с `/v1`), для Anthropic — корень URL: SDK добавляет `/v1/messages`. HTTP допустим для доверенного локального сервера, но не шифрует ключ и сообщения.

Модели задаются вручную: `id | имя | context | max input | max output | yes/no (image input) | reasoning через запятую`. Лимиты и возможности должны соответствовать документации конкретной модели и шлюза. Автоматического получения моделей или их возможностей нет. OpenAI reasoning: `none,low,medium,high,xhigh,max`; Anthropic: `none` или явный `budget:N`, где 1024 ≤ N < max output. Для Chat Completions `none` означает отсутствие запроса reasoning effort. Генерация заголовка использует то же подключение и изолированную сессию без инструментов.

`AgentLoop` сохраняет общий MAF pipeline, локальную историю, инструменты и разрешения чтения при смене транспорта между запросами. При смене подключения, revision, API mode или модели история нормализуется: текст, оригинальные изображения, вызовы и результаты инструментов сохраняются, публичный reasoning превращается в обычный текст с пометкой, закрытые provider-specific блоки не переносятся. Число сообщений не меняется, чтобы сохранить границы rewind. Внутреннее состояние reasoning и cache hit между провайдерами не гарантируются. Если история содержит изображения, переход на модель без image input блокируется.

Принятая очередь держит снимок подключения только в памяти. В `pending.json` и `session.json` ключи не записываются; после перезапуска подключение разрешается по ProviderId из текущих настроек. Восстановленная очередь не запускается автоматически; отсутствующий профиль или модель оставляют её на паузе с ошибкой. Историю можно открыть даже после удаления подключения и продолжить через другую пару провайдер/модель.

## Назначение модели сабагентов

`/models` содержит вкладки «Основной агент» и «Сабагенты» (стандартный `TabControl`). Вкладки переключаются мышью или ← → при фокусе на заголовках; Tab переводит фокус между контролами. Стрелки ↑ ↓ выбирают модель без дополнительного подтверждения, reasoning задаётся стандартным выпадающим списком. Для сабагентов доступны все пары провайдер/модель и вариант «Как у основного агента» с отключённым полем reasoning. У каждой вкладки свой черновик, сохраняющийся при переключении. Общая кнопка «Применить» применяет обе вкладки и закрывает окно; «Отмена» или Esc отменяют все изменения (при открытом dropdown первый Esc закрывает список). При ошибке сохранения окно остаётся открытым с черновиками, действующие настройки не меняются.

`Settings/AgentSettingsStorage.cs` хранит глобальные настройки агента в `~/.lakecode/settings.json`, отдельно от `providers.json`. Сейчас `AgentSettings` содержит версию схемы и необязательный `SubagentModel` (`ProviderId`, `ModelId`, `ReasoningEffort`); null означает наследование. Файл читается до создания UI, сохраняется вне UI-потока атомарной заменой с проверкой отмены до commit, на Linux новый файл имеет права 0600, существующие права сохраняются. Символические ссылки запрещены, повреждение и неподдерживаемая версия не сбрасываются автоматически. Отсутствующий файл означает наследование; фактическое назначение сохраняется при явном сохранении из окна. Выбор основной модели между запусками по-прежнему не сохраняется.

`SubmitMessage` передаёт назначение в Core; `ConversationService` разрешает и фиксирует отдельный снимок подключения, модели и reasoning при принятии сообщения. Смена настройки не меняет принятую очередь, активный запрос и созданные дочерние задачи. Фоновые продолжения сохраняют назначение последнего основного запроса. В очередь записываются только идентификаторы назначения и reasoning, снимок подключения с ключом исключён из JSON. После перезапуска очередь разрешает назначение через текущий registry; отсутствующее подключение/модель или неподдерживаемый reasoning оставляют её на паузе с ошибкой, без скрытого перехода на основную модель. Старые записи без назначения наследуют основной запрос. Снимок дочерней задачи содержит безопасные имена/ID провайдера и модели и reasoning; окно «Сабагенты» показывает фактическую конфигурацию задачи, включая исторические карточки новых сессий.

Ручная проверка назначения:

1. В `/models` открыть вкладку «Сабагенты», выбрать другую пару провайдер/модель стрелками, выбрать reasoning из выпадающего списка и нажать «Применить»; после перезапуска назначение сабагентов должно сохраниться. До применения переключить вкладки и проверить сохранность черновиков. Изменить обе вкладки и нажать «Отмена»/Esc — действующие настройки не должны измениться.
2. Отправить запрос с делегированием: основная модель не меняется, окно «Сабагенты» показывает назначенную модель и reasoning. Проверить также другой провайдер.
3. Поставить сообщение в очередь, сменить назначение, затем выполнить очередь: сообщение использует прежние настройки. Уже запущенный ребёнок и его продолжение после вопроса родителю тоже сохраняют исходную конфигурацию.
4. Вернуть «Как у основного агента» и сохранить; следующие отправки наследуют основную модель и reasoning. Изменение черновика назначения с последующим Esc не должно сохраняться.
5. Удалить назначенную модель или подключение: новая отправка должна показать ошибку с сохранением черновика, а восстановленная очередь — остаться на паузе. Явно переназначить модель через `/models` для новых отправок.
6. Проверить ошибку доступа при сохранении settings.json: окно сохраняет черновик настройки, действующее назначение не меняется.

## Фоновые read-only сабагенты

`Agent/Delegation/DelegationCoordinator.cs` владеет исследовательскими задачами на время сессии основного `AgentLoop`, которым управляет `ConversationService`. Новых зависимостей и универсального event bus нет: переиспользуются MAF-сессии, обычные .NET Tasks, `WorkspaceFiles` и контракты событий ядра. Дочерние потоки читаются независимо; основной экземпляр `AgentLoop` по-прежнему вызывается последовательно.

`delegate(task, context)` теперь всегда запускает задачу в фоне и сразу возвращает JSON `Running` с `taskId`. Промпт основного агента рекомендует самостоятельно делегировать подходящие независимые исследования, продолжая свою непересекающуюся работу; запускать сабагента ради чтения известного файла не нужно. Сабагенты продолжают работу после финального ответа, между пользовательскими сообщениями. Каждый получает отдельную сессию и UUID cache affinity, тот же рабочий корень и инструкции, зафиксированные при создании основной сессии. История разговора не копируется. Подключение, модель и reasoning фиксируются при запуске задачи и сохраняются при продолжениях.

У ребёнка есть только `read_file`, `list_directory`, `grep` и `ask_parent`: без записи, bash, eval, веба, skills, обращения к пользователю и вложенного делегирования. Общий `WorkspaceFiles` сохраняет единые разрешения и запреты внешнего чтения. Запросы разрешения и `ask_tool` сериализуются, чтобы параллельные задачи не открывали конкурирующие интерактивные панели.

### Ожидание и доставка

Основному агенту доступен отдельный прямой инструмент:

```text
wait_subagents(taskIds = null, waitAll = false, timeoutSeconds = 300)
```

- Без `taskIds` выбираются работающие задачи и ещё не доставленные результаты/вопросы. Явные IDs позволяют ждать конкретные задачи.
- По умолчанию ожидание возвращается при первом готовом результате или вопросе, вместе с текущими состояниями остальных выбранных задач.
- `waitAll: true` ждёт все выбранные задачи, но вопрос `NeedsParentInput` всегда завершает ожидание раньше: иначе родитель и исполнитель могли бы ждать друг друга.
- Таймаут — 1..600 секунд. Он возвращает состояния и не отменяет исследования. Ожидание реализовано через сигнал изменения состояния, без sleep и polling.
- Результаты и вопросы, полученные через wait, помечаются доставленными и не создают повторного автоматического уведомления. Повторный явный запрос сохранённого ID может вернуть его состояние снова.

Недоставленные завершения и вопросы автоматически запускают отдельный служебный ход основного агента, когда текущий ход и его сохранение закончились. Пользовательская очередь имеет приоритет. Сервис не входит повторно в занятый `AgentLoop`; уведомления воспринимаются как данные инструмента, а не пользовательские инструкции. Служебный ход использует настройки последнего основного запроса и сохраняется с флагом `IsBackgroundContinuation`. UI показывает отметку «Уведомление фоновых исследований», а не фиктивное сообщение пользователя с полным JSON. Если очередь остановлена или сохранение/контекст заблокированы, автоматическая доставка ожидает возобновления работы. Автоматические продолжения выполняют дополнительные запросы к модели.

### Уточнения, жизненный цикл и UI

`ask_parent(question, reason)` завершает ход ребёнка через штатный `FunctionInvocationContext.Terminate`, с полным чтением потока и записью результата инструмента. Задача становится `WaitingForParent`. Вопрос приходит через `wait_subagents` или автоматическое уведомление с `taskId` и `questionId`. Родитель отвечает из контекста либо через существующий `ask_tool`; `delegate(taskId, questionId, answer)` возобновляет ту же дочернюю сессию в фоне. Повторные/устаревшие ответы отклоняются. Итог — `Completed`, ошибка — `Failed`, отмена — `Cancelled`.

Ограничения: до четырёх незавершённых задач (включая ожидающие родителя), до 32 записей задач в памяти; доставленные завершённые записи освобождаются при новых запусках. На задачу — три уточнения и 32 обращения к модели; каждое исполнение между уточнениями ограничено пятью минутами. Поручение, контекст и ответ родителя — до 16 000 символов каждый; результат — до 32 000. Превышение лимита результата не выдаётся за успешный усечённый итог.

Остановка и прерывание основного запроса отменяют фоновые задачи. Stop работает и между сообщениями. `/new`, переключение сессии, rewind и выход отменяют и дожидаются дочерних операций перед освобождением ресурсов. Завершение обычного ответа, переход к уточнению на границе инструментов и ошибка основного запроса сами по себе не уничтожают фоновые задачи; при ошибке основная очередь остаётся на паузе. Восстановления живых дочерних сессий после перезапуска нет. При открытии истории незавершённые карточки помечаются отменёнными; старые IDs не возобновляются автоматически.

`BackgroundToolCallChanged` связывает снимки с задачей и вызовом инструмента; номер запроса отличает возобновления после уточнений. Запрос, вопрос, ответ родителя и итог выводятся отдельными свёрнутыми блоками в хронологическом порядке, а не переписывают исходную карточку. Снимки сохраняются в последнем ходе на момент события; актуальные задачи доступны через `ConversationState.Delegations`. Разрешение на внешнее чтение показывается в блоке, связанном с исходным вызовом. Завершение основного ответа не помечает работающие делегирования прерванными.

Кнопка «Сабагенты» у правого края хедера показывает число работающих задач, ожидания и ошибки; открывает список задач со статусами. Выбор задачи открывает её ленту в том же немодальном окне: используются компоненты основного чата, Markdown, сворачиваемый reasoning и блоки инструментов, без поля ввода и токенового стриминга. `DelegationActivityChanged` передаёт публичные сообщения после завершения ответа провайдера и структурированные изменения инструментов; границы сообщений сохраняются отдельно. Основной чат продолжает стримиться. Эти события наблюдения не входят в историю основного агента и не сохраняются.

Кнопка «Вернуться в чат» меняет только фокус: окно наблюдателя остаётся поверх основного окна. Для обязательного вопроса или разрешения оно временно уступает передний план, не закрываясь. Закрытие наблюдателя не отменяет работу. Каждая задача хранит собственный прокручиваемый набор компонентов, включая раскрытие блоков; смена задачи не переводит чтение в конец. Автопрокрутка использует то же поведение, что основной чат. Бюджет ленты — 64 000 символов и 128 блоков: удаляются целые старые блоки с явной отметкой, при этом единственный большой блок и незавершённые блоки не обрезаются. Для открытой сохранённой сессии доступны задача, состояние и итог, но не внутренняя лента. Индикатор активности учитывает работающих сабагентов, но их usage не прибавляется к показателям основного запроса.

### Сценарии ручной проверки

Приложение и тесты агентом не запускаются. После сборки вручную проверить:

1. Запустить два независимых исследования: оба `delegate` сразу возвращают IDs, основной агент может продолжить другую работу.
2. Завершить ответ основного агента, пока дети работают, и отправить следующее сообщение: карточки продолжают обновляться; недоставленный итог вызывает служебное продолжение без повторного входа в занятую сессию.
3. Вызвать `wait_subagents` для одного ID и нескольких IDs с `waitAll`; уже полученный результат не должен приходить повторно автоматическим уведомлением.
4. Ребёнок задаёт вопрос при `waitAll`: ожидание возвращается, родитель отвечает и продолжает ту же задачу; другой ребёнок остаётся работающим.
5. Вопрос приходит после финального ответа: родитель автоматически получает уведомление, при необходимости показывает `ask_tool` и возобновляет ребёнка с прежними IDs.
6. Короткий таймаут wait возвращает `Timeout`, а исследование продолжает работу. Пустой список работы и неизвестный ID дают понятную ошибку.
7. Разрешение на внешнюю папку появляется в исходной карточке, в том числе между сообщениями. Одновременно активна только одна панель подтверждения/вопроса; сохранённый запрет не обходится.
8. Остановить работу во время основного запроса и между сообщениями; затем проверить `/new`, переключение сессии, rewind и выход: дети отменяются, поздние события не попадают в новую сессию.
9. Проверить ошибку провайдера и повторный ответ со старым `questionId`; перезапуск не должен автоматически восстанавливать или повторять исследования.
