# LakeCode.Core

Независимое от SharpConsoleUI ядро. CLI ссылается на Core, обратной зависимости нет.

## Три контракта

- **Команды** (`Conversations/ConversationCommand.cs`) — намерения пользователя. `ConversationService.Execute` возвращает принятие команды, а не завершение генерации. Отправка фиксирует неизменяемый профиль подключения, модель, reasoning и собственную копию оригинальных байтов вложений.
- **События** (`Conversations/ConversationEvent.cs`) — произошедшие факты: начало ответа, текстовые фрагменты, вызовы инструментов, завершение, ошибки и запросы решения. `EventOccurred` передаёт envelope с последовательным номером, ID сессии и запроса. Подписка не запускает агент и не воспроизводит старые события.
- **Состояние** (`Conversations/ConversationState.cs`) — текущие флаги выполнения, очередь, доступность операций, заголовок и статистика. `State` доступен сразу; `StateChanged` уведомляет о новом снимке. `GetConversation()` возвращает отдельный снимок истории и восстановленного черновика.

Сервис один раз читает поток MAF и владеет сессией, очередью, отменой, rewind и сохранением. Изменения состояния и публикация уведомлений сериализованы внутренней блокировкой. Обработчики уведомлений должны только ставить обновления в очередь своего представления: не блокировать, не бросать исключения и не выполнять команды синхронно из обработчика. CLI переводит уведомления на UI-поток в `ChatController`.

Ответы на вопросы и разрешения — отдельные команды с ID взаимодействия. Они не ожидают завершения генерации. Повторные и запоздалые решения не принимаются; отмена снимает ожидание и публикует его завершение.

Запрос пользователя сохраняется до внешнего обращения. Следующий запрос начинается после финального сохранения предыдущего. `FinishAsync` ожидает работу и записи очереди, включая финальное сохранение при shutdown. Выполненные побочные эффекты не откатываются при отмене или rewind. Восстановленная очередь видна, но остаётся на паузе до явного запуска.

`Attachments` содержит оригинальные байты и общую проверку изображения; clipboard, выбор файлов, PixelBuffer и превью остаются в CLI. Используется MAF 1.24.0. Формат сессий версии 4 хранит режим запросов и планы вместе с ProviderId и метаданными выбранной модели; версии 1–3 читаются с режимом Build по умолчанию, версии 1 и 2 — как сессии исходного WikiVibe-подключения. Rx-пакеты и универсальный event bus не используются.

## Планирование и подтверждаемая диагностика

`/plan` выбирает Plan для следующих сообщений, `/build` — Build. Справа в футере отображается
только выбранный режим: `plan` или `build`. Переключение не запускает запрос и не меняет активный ход
или принятую очередь. Режим сохраняется в очереди и истории, наследуется фоновыми
продолжениями. При открытии истории CLI выбирает режим последнего хода.

`SystemPromptBuilder` собирает общий контекст один раз, включая глобальный и проектный AGENTS.md.
Каждый запуск получает отдельные Build/Plan-инструкции и свой набор функций через run options:
на уровне MAF-агента инструменты не задаются, поскольку MAF объединяет агентские и request tools.
Plan задаёт исследование причин, проверку гипотез, конкретную последовательность правок и критерии
проверки; не разрешает реализацию даже при запросе «исправь». Skills не расширяют права режима.

В Plan прямые write_file/edit_file отсутствуют и блокируются общим перехватчиком, в том числе через
C# bridge. bash/eval доступны с обязательным description (действие, цель, ожидаемые побочные эффекты)
в обоих режимах. UI показывает описание в карточке. В Plan каждый вызов получает отдельное
подтверждение с точными аргументами, без «разрешить всё». Описание — текст модели, не проверка
безопасности. Подтверждённый код исполняется с правами пользователя: это **не sandbox**.

`ConversationService` сериализует ExecutionApprovalRequested с вопросами и внешними разрешениями
через общий interaction gate; ResolveExecutionApproval относится только к одному ID. Отказ возвращает
явный невыполненный результат; Stop отменяет ожидание, поздние ответы не принимаются. Перед согласием
bash не запускается, eval не отправляет код и не сбрасывает worker. Вложенный bash через eval требует
своего подтверждения; время этого ожидания исключено из execution timeout. При входе в Plan между
ходами eval-worker сбрасывается, его переменные не переносятся из Build (это указано в UI и промпте).

`submit_plan(markdown)` сохраняет неизменяемый план с ID и ревизией в текущем ходе и штатно завершает
stream через MAF Terminate. План выводится как Markdown в истории; он не является файлом проекта.
Кнопка «Реализовать план vN» и `/implement` отправляют ExecutePlan с конкретным ID/ревизией и выбранными
настройками модели. Принимается только актуальный завершённый план после сохранения, когда основной
агент, пользовательская очередь и исследования свободны. Новый Build-запрос содержит копию плана,
явное разрешение реализации и уведомление о возвращённых инструментах. Повторное нажатие не создаёт
второй запрос. Новый пользовательский запрос инвалидирует прежнюю цель кнопки; частичный rewind
удаляет план из сокращённого хода. Полные старые планы остаются в истории, но не дают разрешения записи.

Сессии имеют SchemaVersion 4; pending.json теперь содержит версионированный объект с Messages.
Старые массивы очереди читаются. Старый клиент не сможет молча загрузить новые Plan-запросы как Build.
Неизвестные режимы/версии отклоняются; восстановленная очередь по-прежнему остаётся на паузе.

### Ручная проверка режима планирования

Приложение и тесты агентом не запускаются. После сборки проверить вручную:

1. В Build вызвать bash/eval: описание видно, дополнительного разрешения нет. Пустое description
   отклоняется до исполнения. Старые карточки без description продолжают открываться.
2. Выбрать Plan и попросить исправление: агент исследует и планирует; прямые файловые записи недоступны.
3. Запросить разрешённую проектом диагностику. До подтверждения процесс/код не запускается; отказ
   возвращает «не выполнено». Повторный вызов снова спрашивает. Описание и точные аргументы доступны.
4. В Plan вызвать bash через eval: нужны два разрешения, ожидание второго дольше timeout не уничтожает
   worker. Вызов write_file/edit_file через bridge блокируется. Stop во время ожидания исключает запуск.
5. Подготовить план через submit_plan: виден Markdown, после завершения/сохранения доступна реализация.
   Нажать её дважды: принимается один Build-запрос, инструменты возвращаются, план передан целиком.
6. Переключать режим во время выполнения и при очереди: принятые запросы сохраняют свой режим;
   фоновые продолжения Plan тоже требуют подтверждений. Вход в Plan сбрасывает прежние eval-переменные.
7. Открыть новую и старую сессию, восстановить очередь, сделать rewind до/внутри планирующего хода:
   режимы сохраняются, устаревшее разрешение не используется, частичный план нельзя запустить кнопкой.

## Провайдеры
`Providers/ProviderRegistry.cs` владеет неизменяемыми профилями, `ProviderStorage` сохраняет их в `~/.lakecode/providers.json` независимо от рабочего каталога. Запись атомарная; на Linux каталог создаётся с правами 0700, файл — 0600. Ключи хранятся без шифрования. Повреждённые настройки не сбрасываются автоматически; пути через символические ссылки отклоняются. При отсутствии файла список подключений пуст. Встроенных подключений и чтения ключей из переменных окружения нет: все подключения создаются через конфиг или UI. Исторический ProviderId версий сессий 1/2 сохранён только для чтения старых файлов и не создаёт подключение.

CLI: `/providers` — добавление, изменение и удаление подключений и их моделей; `/models` — выбор пары провайдер/модель. Профиль содержит стабильный ID, revision, название, протокол OpenAI или Anthropic, API mode Responses/ChatCompletions для OpenAI, базовый URL, ключ и `ModelOverrides`. `Models` — вычисляемый список только доступных моделей с разрешёнными характеристиками; в конфиг он не записывается. Сохранение создаёт новую revision и публикует новый профиль после успешной атомарной записи; принятые запросы продолжают использовать старый снимок. Для OpenAI указывается API base URL (обычно с `/v1`), для Anthropic — корень URL: SDK добавляет `/v1/messages`. HTTP допустим для доверенного локального сервера, но не шифрует ключ и сообщения.

На вкладке «Модели» редактора провайдера кнопка «Обновить список» вызывает `ProviderModelDiscovery`: OpenAI — GET `{BaseUrl}/models`, Anthropic — GET `{BaseUrl}/v1/models` с пагинацией `has_more`/`last_id` и `after_id`. Используются ключ и адрес текущего черновика подключения. Discovery получает только API ID, не угадывает лимиты и не выполняет пробную генерацию. HTTP-редиректы запрещены, тело ответа/ключ не показываются в ошибках. Таймаут охватывает весь обход страниц; ошибки оставляют предыдущий список и черновики. Сеть и файловое сохранение не блокируют UI. Обновление работает по явному действию пользователя, без фоновых сетевых обращений при запуске или каждой отправке.

`ModelResolver` разрешает характеристики в порядке: полное `Definition` → явное `CatalogModelId` + `Overrides` → точное совпадение API ID в `ModelCatalog` + `Overrides`. Нечёткого сопоставления нет. API ID никогда не заменяется ID каталога. Отсутствующие поля точечного override наследуются, заданные массивы целиком заменяют исходные. `Definition` требует все характеристики и несовместим с `CatalogModelId`/`Overrides`. Неизвестные/несовместимые модели видны во вкладке настройки, но не попадают в `/models`, пока характеристики не разрешены. Настройка override сама по себе не подтверждает доступность: модель должна присутствовать в discovery либо иметь явный `Manual: true`. Ручной режим предусмотрен для API ID без Models API; сетевые ошибки его не включают.

Список провайдеров имеет отдельные кнопки добавления, изменения и удаления. Редактор содержит вкладки «Подключение» и «Модели», обычные поля вместо строк с `|`, режимы «Автоматически», «Из нашего каталога» и «Полное описание». Пустые поля в первых двух режимах наследуются (исходные значения показаны как placeholders). Черновики моделей сохраняются при переключении строк/вкладок даже при ошибочном вводе. Общее «Сохранить» записывает всё, «Отмена»/Esc ничего не меняет. Удаление подключения требует подтверждения.

`providers.json` использует SchemaVersion 2. Версия 1 читается с преобразованием прежних `Models` в полные `Definition` с `Manual: true`, поэтому существующие настройки и API ID сохраняются; файл перезаписывается новой схемой только при явном сохранении. Discovery хранится отдельно в `~/.lakecode/model-cache/{ProviderId}/{Revision}.json`: API ID, время обновления и хеш идентичности подключения, без ключей и URL. Кэш привязан к revision, адресу, протоколу и ключу; при ручной смене подключения в конфиге старый кэш не применяется. Для записи новой revision сначала создаётся кэш, затем атомарно переключается конфиг, поэтому сбой/отмена до commit конфига не меняет действующее подключение (может остаться неиспользуемый файл кэша). Прежние кэши не удаляются автоматически. В редакторе при смене адреса/ключа/протокола без обновления список discovery не переносится в новое подключение.

Лимиты и возможности каталога/полного описания должны соответствовать документации конкретной модели и шлюза. OpenAI-совместимый протокол допускает reasoning `none,minimal,low,medium,high,xhigh,max`; конкретная модель ограничивает этот набор через `ReasoningEfforts`. Anthropic: `none` или явный `budget:N`, где 1024 ≤ N < max output. Для Chat Completions `none` означает отсутствие запроса reasoning effort. Генерация заголовка использует то же подключение и изолированную сессию без инструментов.

`AgentLoop` сохраняет общий MAF pipeline, локальную историю, инструменты и разрешения чтения при смене транспорта между запросами. При смене подключения, revision, API mode или модели история нормализуется: текст, оригинальные изображения, вызовы и результаты инструментов сохраняются, публичный reasoning превращается в обычный текст с пометкой, закрытые provider-specific блоки не переносятся. Число сообщений не меняется, чтобы сохранить границы rewind. Внутреннее состояние reasoning и cache hit между провайдерами не гарантируются. Если история содержит изображения, переход на модель без image input блокируется.

Принятая очередь держит снимок подключения только в памяти. В `pending.json` и `session.json` ключи не записываются; после перезапуска подключение разрешается по ProviderId из текущих настроек. Восстановленная очередь не запускается автоматически; отсутствующий профиль или модель оставляют её на паузе с ошибкой. Историю можно открыть даже после удаления подключения и продолжить через другую пару провайдер/модель.

### Примеры overrides

Фрагменты внутри профиля в `providers.json` (API ID — ключ словаря):

```json
"ModelOverrides": {
  "company/gpt-6.1-sol": {
    "CatalogModelId": "gpt-6.1-sol",
    "Overrides": {
      "MaxOutputTokens": 16000,
      "ReasoningEfforts": ["low", "medium", "high"]
    }
  },
  "internal/research-model": {
    "Manual": true,
    "Definition": {
      "Name": "Internal Research",
      "ContextWindowTokens": 128000,
      "MaxInputTokens": 112000,
      "MaxOutputTokens": 16000,
      "InputModalities": ["Text"],
      "OutputModalities": ["Text"],
      "ReasoningEfforts": ["none"]
    }
  }
}
```

Характеристики второй записи — пример конфигурации, не утверждение о реальной модели. У первой записи доступность подтверждается discovery; для использования без discovery требуется явный `Manual: true`.

### Ручная проверка провайдеров и discovery

1. Без providers.json открыть `/providers`: список пуст, встроенное подключение/ключ из окружения не появляются. Создать провайдера, переключить вкладки, отменить — записи не появляется.
2. Для OpenAI получить список через `/models`, для Anthropic — список с несколькими страницами. Точное совпадение с каталогом становится доступным в выборе модели, неизвестный ID виден как требующий настройки.
3. Сопоставить API ID шлюза с каталогом, оставить часть полей пустыми, изменить max output и reasoning. После сохранения и перезапуска проверить наследование и фактический API ID в запросе.
4. Полностью описать неизвестную модель; удалить обязательное поле — сохранение показывает ошибку на её вкладке/строке, введённые значения остаются. Исправить и сохранить.
5. Ввести неполную/некорректную настройку, перейти на другую модель и обратно — черновик не теряется. «Сбросить override» возвращает наследование.
6. Проверить 401/404, редирект, таймаут и неправильный JSON Models API: список и overrides остаются прежними, ошибки не содержат ключ/тело ответа. Добавить ручной API ID для шлюза без discovery.
7. Обновить список, где ранее доступный ID исчез: override остаётся, но ID больше не выбирается для работы без явного ручного режима. Принятое ранее сообщение сохраняет свой снимок.
8. Сменить URL/ключ/протокол без обновления: старый discovery не переносится; после обновления получаются модели нового подключения. При ручной правке конфига проверить инвалидирование кэша.
9. Открыть старый providers.json версии 1, проверить модели и возможности, сохранить — версия 2 с полными ручными определениями. Недоступный файл настроек/кэша при записи оставляет действующий профиль прежним.
10. Удалить провайдера из списка: подтверждение, возвращение в список, история остаётся. Восстановленная очередь без соответствующего подключения остаётся на паузе.

## Модель планирования

На вкладке «Планирование» можно отдельно выбрать провайдера, модель и reasoning. Назначение сохраняется для всех проектов. «Как у основного агента» снимает отдельный выбор: следующие Plan-запросы используют текущую основную модель и её reasoning, включая последующие изменения основного выбора. Build и реализация готового плана через `/implement` или кнопку используют основную модель, а не `PlanModel`. Shift+Tab и нижняя строка по-прежнему относятся к основному выбору; reasoning отдельного Plan-назначения меняется через `/models`.

CLI разрешает `PlanModel` до подготовки файлов и передаёт фактические модель, провайдер и reasoning через существующие поля `SubmitMessage`. Лимит файлов и поддержка изображений проверяются по фактической модели. Недоступное явное назначение вызывает ошибку с сохранением черновика, без скрытого перехода на основную модель. Очередь сохраняет фактические ID и reasoning запроса; изменение `PlanModel` не переназначает принятые сообщения. Назначение сабагентов независимо: без него они наследуют фактическую модель родительского запроса, в том числе Plan. Фоновые продолжения используют конфигурацию последнего запроса.

Ручная проверка планирования:

1. Открыть старый settings.json без `PlanModel`: вкладка наследует основной выбор, назначение сабагентов сохранено.
2. Выбрать отдельные модель, провайдер и reasoning, применить и перезапустить: назначение сохранено, Plan использует его, Build — основную модель.
3. Вернуть «Как у основного агента», применить и изменить основную модель/reasoning: следующие Plan-запросы наследуют новый выбор, поле reasoning на вкладке планирования отключено.
4. Изменить три вкладки и переключать их: черновики сохраняются; Отмена/Esc ничего не применяет. При открытом dropdown первый Esc закрывает только список. При ошибке сохранения настройки не меняются, черновики остаются в окне.
5. Удалить назначенное подключение/модель или сделать reasoning неподдерживаемым: отправка Plan показывает ошибку, черновик сохранён. Выбор наследования восстанавливает отправку.
6. Отправить Plan с файлами и изображениями: ограничения проверяются по Plan-модели; несовместимые вложения не принимаются, черновик остаётся.
7. Поставить Plan в очередь и изменить назначение/режим, в том числе во время подготовки файлов: запрос сохраняет захваченные модель, reasoning и режим. После восстановления очереди используются сохранённые ID, а не новое назначение.
8. Получить готовый план и запустить `/implement` или кнопку: создаётся Build-запрос на основной модели.
9. Делегировать из Plan без отдельного назначения сабагентов и с ним: сначала наследуется Plan-модель, затем используется явное назначение сабагентов. Фоновые продолжения сохраняют конфигурацию родительского запроса.

## Назначение моделей планирования и сабагентов

`/models` содержит вкладки «Основной агент», «Планирование» и «Сабагенты» (стандартный `TabControl`). Вкладки переключаются мышью или ← → при фокусе на заголовках; Tab переводит фокус между контролами. Стрелки ↑ ↓ выбирают модель без дополнительного подтверждения, reasoning задаётся стандартным выпадающим списком. Для планирования и сабагентов доступны все пары провайдер/модель и вариант «Как у основного агента» с отключённым полем reasoning. У каждой вкладки свой черновик, сохраняющийся при переключении. Общая кнопка «Применить» применяет все три вкладки и закрывает окно; «Отмена» или Esc отменяют все изменения (при открытом dropdown первый Esc закрывает список). При ошибке сохранения окно остаётся открытым с черновиками, действующие настройки не меняются.

`Settings/AgentSettingsStorage.cs` хранит глобальные настройки агента в `~/.lakecode/settings.json`, отдельно от `providers.json`. Сейчас `AgentSettings` содержит версию схемы и необязательные `PlanModel` и `SubagentModel` (`ProviderId`, `ModelId`, `ReasoningEffort`); null означает наследование. Старые файлы без `PlanModel` читаются без изменения версии схемы и наследуют основной выбор для Plan. Файл читается до создания UI, сохраняется вне UI-потока атомарной заменой с проверкой отмены до commit, на Linux новый файл имеет права 0600, существующие права сохраняются. Символические ссылки запрещены, повреждение и неподдерживаемая версия не сбрасываются автоматически. Отсутствующий файл означает наследование; фактическое назначение сохраняется при явном сохранении из окна. Выбор основной модели между запусками по-прежнему не сохраняется.

`SubmitMessage` передаёт назначение в Core; `ConversationService` разрешает и фиксирует отдельный снимок подключения, модели и reasoning при принятии сообщения. Смена настройки не меняет принятую очередь, активный запрос и созданные дочерние задачи. Фоновые продолжения сохраняют назначение последнего основного запроса. В очередь записываются только идентификаторы назначения и reasoning, снимок подключения с ключом исключён из JSON. После перезапуска очередь разрешает назначение через текущий registry; отсутствующее подключение/модель или неподдерживаемый reasoning оставляют её на паузе с ошибкой, без скрытого перехода на основную модель. Старые записи без назначения наследуют основной запрос. Снимок дочерней задачи содержит безопасные имена/ID провайдера и модели и reasoning; окно «Сабагенты» показывает фактическую конфигурацию задачи, включая исторические карточки новых сессий.

Ручная проверка назначения:

1. В `/models` открыть вкладку «Сабагенты», выбрать другую пару провайдер/модель стрелками, выбрать reasoning из выпадающего списка и нажать «Применить»; после перезапуска назначение сабагентов должно сохраниться. До применения переключить вкладки и проверить сохранность черновиков. Изменить все три вкладки и нажать «Отмена»/Esc — действующие настройки не должны измениться.
2. Отправить запрос с делегированием: основная модель не меняется, окно «Сабагенты» показывает назначенную модель и reasoning. Проверить также другой провайдер.
3. Поставить сообщение в очередь, сменить назначение, затем выполнить очередь: сообщение использует прежние настройки. Уже запущенный ребёнок и его продолжение после вопроса родителю тоже сохраняют исходную конфигурацию.
4. Вернуть «Как у основного агента» и сохранить; следующие отправки наследуют основную модель и reasoning. Изменение черновика назначения с последующим Esc не должно сохраняться.
5. Удалить назначенную модель или подключение: новая отправка должна показать ошибку с сохранением черновика, а восстановленная очередь — остаться на паузе. Явно переназначить модель через `/models` для новых отправок.
6. Проверить ошибку доступа при сохранении settings.json: окно сохраняет черновик настройки, действующее назначение не меняется.

## Фоновые read-only сабагенты

`Agent/Delegation/DelegationCoordinator.cs` владеет исследовательскими задачами на время сессии основного `AgentLoop`, которым управляет `ConversationService`. Новых зависимостей и универсального event bus нет: переиспользуются MAF-сессии, обычные .NET Tasks, `WorkspaceFiles` и контракты событий ядра. Дочерние потоки читаются независимо; основной экземпляр `AgentLoop` по-прежнему вызывается последовательно.

`delegate(task, context)` теперь всегда запускает задачу в фоне и сразу возвращает JSON `Running` с `taskId`. Промпт основного агента рекомендует самостоятельно делегировать подходящие независимые исследования, продолжая свою непересекающуюся работу; запускать сабагента ради чтения известного файла не нужно. Сабагенты продолжают работу после финального ответа, между пользовательскими сообщениями. Каждый получает отдельную сессию и UUID cache affinity, тот же рабочий корень и инструкции, зафиксированные при создании основной сессии. История разговора не копируется. Подключение, модель и reasoning фиксируются при запуске задачи и сохраняются при продолжениях.

У ребёнка есть только `read_file`, `list_directory`, `grep` и `ask_parent`: без записи, bash, eval, веба, skills, обращения к пользователю и вложенного делегирования. Общий `WorkspaceFiles` сохраняет единые разрешения и запреты внешнего чтения. Запросы разрешения и `ask_tool` сериализуются, чтобы параллельные задачи не открывали конкурирующие интерактивные панели.

### Ожидание и доставка

Основному агенту доступен отдельный прямой инструмент:

```text
wait_subagents(taskIds = null, waitAll = false, timeoutSeconds = 300)
```

- Без `taskIds` выбираются работающие задачи и ещё не доставленные результаты/вопросы. Явные IDs позволяют ждать конкретные задачи.
- По умолчанию ожидание возвращается при первом готовом результате или вопросе, вместе с текущими состояниями остальных выбранных задач.
- `waitAll: true` ждёт все выбранные задачи, но вопрос `NeedsParentInput` всегда завершает ожидание раньше: иначе родитель и исполнитель могли бы ждать друг друга.
- Таймаут — 1..600 секунд. Он возвращает состояния и не отменяет исследования. Ожидание реализовано через сигнал изменения состояния, без sleep и polling.
- Результаты и вопросы, полученные через wait, помечаются доставленными и не создают повторного автоматического уведомления. Повторный явный запрос сохранённого ID может вернуть его состояние снова.

Недоставленные завершения и вопросы автоматически запускают отдельный служебный ход основного агента, когда текущий ход и его сохранение закончились. Пользовательская очередь имеет приоритет. Сервис не входит повторно в занятый `AgentLoop`; уведомления воспринимаются как данные инструмента, а не пользовательские инструкции. Служебный ход использует настройки последнего основного запроса и сохраняется с флагом `IsBackgroundContinuation`. UI показывает отметку «Уведомление фоновых исследований», а не фиктивное сообщение пользователя с полным JSON. Если очередь остановлена или сохранение/контекст заблокированы, автоматическая доставка ожидает возобновления работы. Автоматические продолжения выполняют дополнительные запросы к модели.

### Уточнения, жизненный цикл и UI

`ask_parent(question, reason)` завершает ход ребёнка через штатный `FunctionInvocationContext.Terminate`, с полным чтением потока и записью результата инструмента. Задача становится `WaitingForParent`. Вопрос приходит через `wait_subagents` или автоматическое уведомление с `taskId` и `questionId`. Родитель отвечает из контекста либо через существующий `ask_tool`; `delegate(taskId, questionId, answer)` возобновляет ту же дочернюю сессию в фоне. Повторные/устаревшие ответы отклоняются. Итог — `Completed`, ошибка — `Failed`, отмена — `Cancelled`.

Ограничения: до четырёх незавершённых задач (включая ожидающие родителя), до 32 записей задач в памяти; доставленные завершённые записи освобождаются при новых запусках. На задачу — три уточнения и 32 обращения к модели; каждое исполнение между уточнениями ограничено пятью минутами. Поручение, контекст и ответ родителя — до 16 000 символов каждый; результат — до 32 000. Превышение лимита результата не выдаётся за успешный усечённый итог.

Остановка и прерывание основного запроса отменяют фоновые задачи. Stop работает и между сообщениями. `/new`, переключение сессии, rewind и выход отменяют и дожидаются дочерних операций перед освобождением ресурсов. Завершение обычного ответа, переход к уточнению на границе инструментов и ошибка основного запроса сами по себе не уничтожают фоновые задачи; при ошибке основная очередь остаётся на паузе. Восстановления живых дочерних сессий после перезапуска нет. При открытии истории незавершённые карточки помечаются отменёнными; старые IDs не возобновляются автоматически.

`BackgroundToolCallChanged` связывает снимки с задачей и вызовом инструмента; номер запроса отличает возобновления после уточнений. Запрос, вопрос, ответ родителя и итог выводятся отдельными свёрнутыми блоками в хронологическом порядке, а не переписывают исходную карточку. Снимки сохраняются в последнем ходе на момент события; актуальные задачи доступны через `ConversationState.Delegations`. Разрешение на внешнее чтение показывается в блоке, связанном с исходным вызовом. Завершение основного ответа не помечает работающие делегирования прерванными.

Кнопка «Сабагенты» у правого края хедера показывает число работающих задач, ожидания и ошибки; открывает список задач со статусами. Выбор задачи открывает её ленту в том же немодальном окне: используются компоненты основного чата, Markdown, сворачиваемый reasoning и блоки инструментов, без поля ввода и токенового стриминга. `DelegationActivityChanged` передаёт публичные сообщения после завершения ответа провайдера и структурированные изменения инструментов; границы сообщений сохраняются отдельно. Основной чат продолжает стримиться. Эти события наблюдения не входят в историю основного агента и не сохраняются.

Кнопка «Вернуться в чат» меняет только фокус: окно наблюдателя остаётся поверх основного окна. Для обязательного вопроса или разрешения оно временно уступает передний план, не закрываясь. Закрытие наблюдателя не отменяет работу. Каждая задача хранит собственный прокручиваемый набор компонентов, включая раскрытие блоков; смена задачи не переводит чтение в конец. Автопрокрутка использует то же поведение, что основной чат. Бюджет ленты — 64 000 символов и 128 блоков: удаляются целые старые блоки с явной отметкой, при этом единственный большой блок и незавершённые блоки не обрезаются. Для открытой сохранённой сессии доступны задача, состояние и итог, но не внутренняя лента. Индикатор активности учитывает работающих сабагентов, но их usage не прибавляется к показателям основного запроса.

### Сценарии ручной проверки

Приложение и тесты агентом не запускаются. После сборки вручную проверить:

1. Запустить два независимых исследования: оба `delegate` сразу возвращают IDs, основной агент может продолжить другую работу.
2. Завершить ответ основного агента, пока дети работают, и отправить следующее сообщение: карточки продолжают обновляться; недоставленный итог вызывает служебное продолжение без повторного входа в занятую сессию.
3. Вызвать `wait_subagents` для одного ID и нескольких IDs с `waitAll`; уже полученный результат не должен приходить повторно автоматическим уведомлением.
4. Ребёнок задаёт вопрос при `waitAll`: ожидание возвращается, родитель отвечает и продолжает ту же задачу; другой ребёнок остаётся работающим.
5. Вопрос приходит после финального ответа: родитель автоматически получает уведомление, при необходимости показывает `ask_tool` и возобновляет ребёнка с прежними IDs.
6. Короткий таймаут wait возвращает `Timeout`, а исследование продолжает работу. Пустой список работы и неизвестный ID дают понятную ошибку.
7. Разрешение на внешнюю папку появляется в исходной карточке, в том числе между сообщениями. Одновременно активна только одна панель подтверждения/вопроса; сохранённый запрет не обходится.
8. Остановить работу во время основного запроса и между сообщениями; затем проверить `/new`, переключение сессии, rewind и выход: дети отменяются, поздние события не попадают в новую сессию.
9. Проверить ошибку провайдера и повторный ответ со старым `questionId`; перезапуск не должен автоматически восстанавливать или повторять исследования.
