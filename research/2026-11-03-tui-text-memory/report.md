# Как уменьшить аллокации текста в SharpConsoleUI

Рекомендация: **без новой зависимости**. Сохранить ScrollToBottom и публичный API,
но заменить внутреннее представление строк. Исследование выполнено 2026-11-03;
это архитектурное решение по исходникам, не измеренный результат реализации.

Нынешние оптимизации убрали часть повторных разборов, но сохранили дорогое
представление: полный список Cell, копии логических строк и дополнительные
копии перенесённых строк. Cell уже является struct. Проблема — массивы и
повторяющиеся данные внутри них, а не отдельная managed-аллокация каждого символа.
Основание: локальные MarkupParser.cs, MarkupControl.Sources.cs, Layout/Cell.cs
и профиль /tmp/lakecode-2193624-allocations-b.txt.

## Предлагаемая переработка

1. **Переносы как описания диапазонов.** Внутри библиотеки заменить
   `List<List<Cell>>` на layout из записей: источник, начало, длина, экранная
   ширина, признак мягкого переноса, фон заполнения конца строки. Первый
   миграционный шаг может ссылаться на нынешний единый буфер ячеек: он уберёт
   GetRange при переносах без одновременной замены всего парсера. Это ещё не
   конечное решение для ParseCore/AddWithResize.

2. **Текст и стили как основное хранилище.** Затем заменить единый Cell-буфер
   на принадлежащие документу текстовые chunks, границы графем, hard-line index,
   диапазоны стилей и ссылки по идентификаторам. Цвет/стиль не нужно повторять
   в каждой ячейке всех ширин. В C# пригодны массивы небольших struct и
   ReadOnlyMemory поверх хранилища с определённым владельцем. Не нужен новый
   dependency или обязательный rope на первом этапе.

3. **Отдельно layout и запись в экран.** MeasureDOM получает высоту/ширину из
   описаний строк. PaintDOM находит первый видимый ряд по индексу и пишет
   видимые графемы прямо в существующий CharacterBuffer. Выделение добавляется
   во время записи, не копированием Cell-строки. Copy/selection/hit testing
   работают по отображению экранных координат в исходные диапазоны. Историю
   за пределами viewport не удаляем. ScrollToBottom синхронно запрашивает
   актуальную высоту через этот же layout: его вызов и результат сохраняются.

4. **Инвалидация по изменившемуся содержимому.** После смены хранения делить
   Markdown на блоки с версиями. При append переиспользовать независимые блоки,
   переразбирать изменившийся хвост и зависимые блоки, обновлять суммы высот.
   Для прежнего SetMarkdown определять append по отношению к предыдущему
   значению; при редактировании в середине использовать корректный более широкий
   пересчёт. Проверка префикса и создание полного входного string у вызывающей
   стороны всё ещё могут стоить O(N): сохраняемый API не даёт оснований обещать
   строгую O(delta) для всего пути.

Это наша схема применения найденных приёмов, а не утверждение, что одна из
изученных библиотек реализует все пункты именно так.

| Parsing/MarkdownToMarkup.cs | Позднее дать внутреннему renderer возможность выпускать styled runs из AST без промежуточной markup-строки; публичный Convert сохранить |
| Layout/CharacterBuffer.cs | Внутренний путь записи диапазона/графем без IEnumerable-обёрток и промежуточных List<Cell> |

Публичные Parse/ParseLines остаются совместимыми материализующими адаптерами:
по явному вызову создают новые независимые mutable List<Cell>. Внутренний
MarkupControl перестаёт использовать этот дорогой формат как основное хранилище.
Публичный Cell не меняется. SetMarkdown остаётся синхронным по текущему контракту.

## Границы корректности и памяти

Инкрементальный Markdown требует правил зависимостей. Определение reference-link
может прийти после использующего его блока — это прямо разрешает CommonMark.
Нельзя безусловно замораживать всё, кроме последнего блока. Нужны invalidation
по определениям/расширениям и fallback для неоднозначных конструкций.
[S8](https://spec.commonmark.org/0.31.2/#link-reference-definitions)

Нужно различать UTF-16 offset, графему и экранную колонку. Перенос не разрывает
ZWJ/VS16/широкие символы, а range сохраняет информацию о пропущенных пробелах.
Публичное поведение узкого viewport, FillToWidth, links и copy задаёт наш текущий
контракт; алгоритм другой библиотеки не является готовой заменой.

Диапазоны не должны удерживать целую старую строку SetMarkdown для каждого
сохранённого блока: ReadOnlyMemory на разные полные версии документа способен
создать новый источник удержания памяти. Хранилище — стабильные owned chunks;
предыдущие цельные снимки освобождаются. Доступ paint/selection и фоновый measure
должны иметь явное время жизни snapshot.

ArrayPool подходит для ограниченной рабочей памяти, но не устраняет повторный
разбор/копирование. Rent может вернуть массив больше запроса; Return не гарантирует
возврата памяти ОС. После Return буфер больше не принадлежит вызывающему коду;
Cell содержит managed-ссылку Combiners, которую нельзя случайно удерживать.
Публичные mutable результаты и snapshots с читателями нельзя возвращать в пул.
[S9](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1.rent?view=net-10.0),
[S10](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1.return?view=net-10.0)

## Порядок и критерии результата

Сначала диапазоны переноса вместе с адаптацией paint/copy; затем компактный
источник и вывод видимой области; затем инкрементальные Markdown-блоки.
Пулы применить к оставшимся краткоживущим буферам с ограничением удерживаемой
ёмкости. Не менять ScrollToBottom, частоту пользовательских обновлений или
формат истории как способ скрыть проблему.

На одинаковой сессии и одинаковом потоке сравнивать allocated bytes/sec,
живую кучу, память после сворачивания и повторной смены ширины. Ожидаемые
структурные признаки: исчезновение GetRange из переноса; измерение не создаёт
Cell[] всего документа; экранные ячейки ограничены видимой областью; стабильные
блоки не пересоздаются при append. Абсолютный размер RSS и процент ускорения
до реализации и измерений не обещаются.

Проверены исходники и документация; сторонние библиотеки не запускались,
пакеты не устанавливались, runtime-бенчмарки не выполнялись. Код LakeCode и
SharpConsoleUI в этом исследовании не менялся. Подробности доступа и версии —
в [evidence.md](evidence.md), вопросы — в [plan.md](plan.md).
